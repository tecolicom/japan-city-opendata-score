# 指標の正典 — コア 5 軸と由来の扱い

自治体が web で発信する情報が「**実際に使えるか**」を測る指標のコア定義。評価は `(自治体 × 情報領域 × 配信元)` の組ごとに付く。

この文書は**コア (軸名・配点・思想・由来・プロファイル規約)** だけを定める。段階表 (何点が何を意味するか) は書かない。それは領域プロファイルの仕事である (§6)。

## 1. 思想

- 測るのは「オープンデータとして立派か」ではなく「**市民・開発者が実際に使えるか**」。
- 公式カタログに載っていなくても、機械可読で取得できれば得点する。
- 評価は必ず**実測**に基づく。自己申告・アンケートは根拠にしない。
- スコアは改善の材料であって成績表ではない。低い自治体を非難する趣旨ではない。

## 2. コア 5 軸 (100 点)

全領域で同じ定義。領域をまたぐ横断比較はこの軸名と得点で行う。**配点は変えない。**

| 軸 | 名称 | 配点 | W3C DQV / ISO/IEC 25012 対応 |
|---|---|---|---|
| A | 取得性 (Access) | 20 | Availability (Zaveri ↔ ISO exactMatch) |
| B | 機械可読性 (Format) | 25 | Interoperability / Representational |
| C | 粒度・完全性 (Granularity) | 20 | Precision (`dqv:precision`) + Completeness |
| D | ライセンス (License) | 20 | Licensing (Zaveri) |
| E | 検証可能性 (Verifiability) | 15 | Traceability / Trustworthiness |
| | 合計 | **100** | |

各軸が測るもの (一行定義。段階は §6 のプロファイルが持つ):

- **A**: プログラムから直接取得できるか
- **B**: データの形式が機械可読か
- **C**: どこまで書いてあるか (粒度と欠落のなさ)
- **D**: 再利用の法的確実性
- **E**: 正しさを独立に確かめられるか

軸名・配点・思想は `japan-gomi-data/docs/opendata-quality-index.md` から継承している。

## 3. 何を共通にし、何を共通にしないか

**共通にするもの**: 軸名、配点、思想、由来の扱い (§4)。

**共通にしないもの**: **段階表とキャップ規則。これらは領域プロファイルが持つ。**

**ランク閾値 (S〜E) は共通側**に置く (§3.1)。ランクを領域ごとに変えると横断比較が壊れるため。キャップ (欠落の質による上限) は本質的に領域固有なので、プロファイル側に置く。

理由: ごみの段階表は領域固有の語彙に直結している (C 軸は `rules / dates / weekday-rules / partial`、B 軸は `source_type` 列挙、キャップ規則は「可燃ごみの日程が無い」)。イベント領域に写像先が無い。領域非依存の抽象段階表は**書かない** — 書けばごみ側の正典の書き換えと再採点が入り込む。

横断比較は軸名と得点のレベルで行う。

### 3.1 コア合計とランク

**コア合計 (100 点満点)** は、**5 軸すべてが値を持つとき (= 由来が `unknown` でない) だけ**出す。1 軸でも `unknown` なら**合計は null (合計なし)**。部分和を出さない (部分和を 100 点満点で見せると、未調査の行が低得点に見える)。

**ランク閾値 (コア共通。`japan-gomi-data/docs/opendata-quality-index.md` の値を継承し、変えない)**:

| ランク | 点 |
|---|---|
| S | 90〜100 |
| A | 75〜89 |
| B | 60〜74 |
| C | 40〜59 |
| D | 20〜39 |
| E | 0〜19 |

**キャップ規則はプロファイルが持つ。** 例: ごみの `core_missing` (可燃ごみの日程が無い → 19 点を上限) は領域固有の規則で、ごみのプロファイルの一部。

**`score.mjs` の責務**: コア軸点の合計と、共通ランク閾値の適用まで。キャップと段階表はプロファイル定義から読む。

## 4. 由来 (provenance)

各軸の値は必ず由来を持つ。測っていない値を測った値のように見せないための、本指標の中核要件。

| 由来 | 意味 |
|---|---|
| `measured` | その自治体 (配信元) で実際に取得して確認した |
| `inherited` | CMS family の代表実測から継承した。family id と代表 handle を必ず記録 |
| `estimated` | 状況証拠からの推定。根拠を notes に書く |
| `unknown` | 未調査。**0 点ではない。「測っていない」である** |

### `unknown` は 0 点ではない

`unknown` を低得点として扱ってはならない。未調査の自治体が「悪い」ように見えるのは評価として誤りであり、貢献者も遠ざける。`unknown` の軸は**得点を持たない** (null)。点数に換算せず、集計の分子にも入れない。

### ごみ側の `unknown` との関係

同じ語が別の概念に当たっている。混同しないこと。

- ごみ側の `unknown` は**入力の状態** (台帳の `license: unknown` 等)。`triage-score.mjs` は保守値を割り当てて `estimated` フラグを立てる (例: `D = 10; if (lic === 'unknown') est.add('D')`)。**値を持つ。**
- 本書の `unknown` は**由来の値**で、軸を測っていないことを指す。**値を持たない (null)。**

| ごみ側 | 本書 |
|---|---|
| 入力が unknown → 保守値 + `estimated` フラグ | `estimated` (状況証拠からの推定。値を持つ) |
| 対応物なし (実際に調査した自治体しか採点しない) | `unknown` (未調査。値を持たない) |

ごみ側の `estimated` 運用と本書の `estimated` は対応する (ただしごみ側は notes を要求せず、本書は要求する。ごみ既存スコアの notes 欠落は違反ではない)。本書の `unknown` にはごみ側に対応物が無い。`score.mjs` は両者を統一しようとしないこと。ごみ側は再採点しない。

### 継承できる軸

F / G は動的プロファイル (§7) にのみ存在する。**静的領域で継承できるのは A のみ。**

| 軸 | 継承 | 理由 |
|---|---|---|
| A. 取得性 | 可 | CMS が取得口の形を決める |
| F. 更新検知性 | 可 | 条件付き GET の対応は CMS 実装依存 |
| G. 継続性 | 可 | 恒久 URL か・障害の出方は CMS/基盤依存 |
| B. 機械可読性 | **不可** | 中身の形式は自治体の運用が決める |
| C. 粒度・完全性 | **不可** | 同じ CMS でも書き込む内容が違う |
| D. ライセンス | **不可** | 自治体ごとの判断 |
| E. 検証可能性 | **不可** | その配信元が検証できる出典を持つかは配信元ごとの事情で、CMS が決めない |

**継承できるのは A / F / G のみ。** B / C / D / E に `inherited` は付けられない。

運用規則:

- **`inherited` は assessment ファイルに書いてよい。** ただし `inherited_from: {family_id, representative_handle}` を必ず伴う。`inherited` を持てるのは A / F / G のキーだけ。
- **禁じているのは、調べていない自治体の assessment ファイルを一括で機械生成すること。** family 所属を確認した配信元について、継承したと明示的に記録するのは正当な測定行為で、両者は別物。設計書 §5.5 の「機械生成しない」は一括生成の禁止であって、個別の `inherited` 記録の禁止ではない。
- family 所属は基盤レジストリ (自治体ごとの web 基盤を記録する層。`web.yaml`) に持つ。assessment を置いていない配信元の A / F / G は、利用側がそこから導出できる。

### 集計の規則

公開する集計値には `measured` のみを含め、母数を明示する。集計の単位は 2 種類:

- **軸ごとの集計** (各軸の分布・平均): **軸単位で `measured` のみ**を分子にし、母数を併記する。
- **コア合計の集計** (合計点の分布): **5 軸すべてが `measured` の行のみ**を対象にし、母数を併記する。

(行単位に統一すると、1 軸でも `inherited` があるだけで行全体が落ち、母数が不必要に痩せる。)

## 5. 測定地点

A 軸と F 軸の値は測定地点に依存する (国外 IP からだけ 403 を返す配信元がある)。

- `observed_from` は **A 軸と F 軸にのみ**付ける (この 2 軸だけが測定地点に依存する)。**基準は `jp-residential` (国内からの実測)。既定値もこれ。**
- `inherited` の A / F の `observed_from` は、**代表実測の測定地点**を指す。どの実測かは `inherited_from` が特定する。
- 国外 IP (CI) からの遮断はスコアに入れない。ただし遮断は「取れない」と等価の実害を生むので、注記ではなく**構造化フィールド**で持つ (例: `reachability: {overseas_rest: blocked}`)。利用側が自動化の可否を判断できる形にする。
- 将来の CI 測定のため、`observed_from: overseas-ci` を併置できる schema にしておく。

## 6. プロファイル

評価は領域ごとの**プロファイル**を持つ。プロファイルは、コア 5 軸の**段階表とキャップ規則**と、領域特性に応じた**追加軸**を定義する。

| プロファイル | 追加軸 | 段階表の所在 |
|---|---|---|
| 静的領域 | なし (コア 5 軸のみ) | `japan-gomi-data/docs/opendata-quality-index.md` |
| 動的領域 | F 更新検知性 / G 継続性 (代理指標版 `g_proxy`) | `schema/profiles/dynamic.yaml` (§7) |

- **静的領域プロファイルの段階表は `japan-gomi-data/docs/opendata-quality-index.md` を参照する。** 現状のまま残し、本書のコアを参照する側とする。**ごみ側の再採点は行わない。** 既存スコアは定義を変えずに本体系に取り込まれる。
- 段階表の実装が 2 repo に分かれるとドリフトするため、`score.mjs` はコア部分の算出のみを担い、段階表はプロファイル定義から読む。
- 領域とプロファイルの対応は `schema/domains.yaml` の `profile` が持つ 。値の列挙は `schema/domains.yaml` と `schema/domains.schema.json` が正典で、ここでは重複して定義しない。

## 7. 動的プロファイルの追加軸 (F・G)

イベント・お知らせのように継続的に変化する情報のための追加軸。

| 軸 | 名称 | 対応 | 測るもの |
|---|---|---|---|
| F | 更新検知性 | Timeliness (Zaveri) ↔ Currentness (ISO) | 更新を安く確実に検知できるか。条件付き GET (ETag / Last-Modified)、フィードの有無、更新日時の明示 |
| G | 継続性 | Availability の時間軸 + Recoverability | 時間を通じて取り続けられるか。恒久 URL か、形式変更の予告、既知の障害 |

**F / G の段階表の正典は `schema/profiles/dynamic.yaml`** (版 `revision`、現行 `2026-10-24.1`)。点数の正典は段階表で、本書は決め方と、何が実測の裏付けを持ち何が持たないかを書く (点数の写しは段階表を変えたとき追従させる)。尺度は F / G とも 0〜10 で、コア 100 点には足さない (§8)。

### 7.1 段階表は実測の分布から決めた — ただし実測は低い段に届かなかった

埼玉 30 自治体の実測 (`docs/measurements/saitama-2026-10-24.md`) と、assessment に記録した 16 配信元の facts (`node scripts/score.mjs --pref saitama --distribution`) を見て決めた。

| 事実 | 観測された分布 | 観測が無かったもの |
|---|---|---|
| 条件付き GET (トップページ。30 自治体) | 両方 19 / Last-Modified のみ 11 | **ETag のみ 0 / なし 0** |
| 条件付き GET (assessment の 16 配信元) | 両方 9 / Last-Modified のみ 7 | 同上 |
| フィードの HTTP ステータス | 502 が 4 件 (ページ上のリンクで確認できたのは hanno / iruma の 2 件。fukaya / gyoda は family の URL パターンから組み立てた 1 回きりの確認) | 200 の観測 0 件 |
| `stable_url` / `feed_format` / `edition_label` / `license_text` / `standard_od` | **0 件 (未観測)** | すべて |

**実測だけでは F の低い段も G の大半も埋まらない。** 観測が届いた段と、設計判断で置いた段を、段階表の各段の `basis` で区別する。

- `basis: observed` … 実データの facts がその段に当たっている。
- `basis: design` … 設計判断で置いた未検証の段。観測が 1 件も無い。

`basis` は実データと突き合わせる (`scripts/__tests__/score.test.mjs`)。observed の段に実データが 1 件も当たらない、または design の段に実データが当たっていれば、`npm test` が落ちる。**観測が付いた時に、design を observed に直す作業が強制される。** 測っていない値を測った値のように見せないという本 repo の原則を、段階表自体にも適用している。

### 7.2 F (更新検知性) の段階

観測の地点で由来が変わる。`conditional_get_scope` (facts) が観測地点を持つ。

- `scope=source` (配信元の URL そのもので観測): 両方 10 / ETag のみ・Last-Modified のみ 6 / なし 0。**この scope の実データはまだ無く、全段 design。**
- `scope=site-top` (自治体サイトのトップページで観測。現在の 16 配信元すべて): 点数は同じで、由来は **`estimated`** (同じサイト基盤なので配信元も同様と推定。配信元そのもので条件付き GET を確認していない)。`notes` に根拠を書く。
  - both (10) と last-modified (6) は observed。etag (6) と none (0) は design。

「両方」と「Last-Modified のみ」の点差 (10 対 6) 自体が設計判断。実測が示したのは、この 2 つが現実に分かれて存在すること (19 対 11) だけで、差の大きさは示していない。ETag のみと Last-Modified のみに優劣を付ける根拠は実測に無いので同点にした。

**帰結: 現時点の F は全 16 行が `estimated` なので、`measured` のみを数える集計では F の母数は 0。** 配信元そのもので条件付き GET を測った行が出て初めて `measured` が現れる。

フィードの有無・更新日時の明示は、記録する facts が無い (フィードは 502 で観測できなかった) ので、段を置かなかった。観測できる事実が出てから足す。

### 7.3 G の段階 — `g_proxy` (代理指標版)

G は本来「観測期間中の可用性」で、1 回の訪問では測れない。時系列観測 (観測窓・履歴・差分検知) は監視手法の層 (本スライスの範囲外。別途設計する) の仕事なので、初回は単発訪問で取れる代理指標だけで定義し、**`g_proxy`** という別名で持つ。代理指標は次の 3 つ:

- 恒久 URL か (クエリパラメータ依存・年度別パス・セッション依存の有無)
- 形式変更の予告の有無 (版表記、`edition` の明示)
- 既知の障害 (実地で観測した停止事象。family に記録済みのものを参照)

後から時系列版の G を足せる形にしておく。以下は実測後に確定した段階。

axes のキーは `G` のままだが、段階表は `axis_aliases: {G: g_proxy}` を宣言し、CSV の列名は `g_proxy` と書く。時系列版の G (監視層) と取り違えないための名前。

- 5xx (ページ上のリンクで確認したフィード) … 0。**observed。** hanno / iruma の 2 行。観測は 1 回で、障害の継続期間は `families/*.yaml` の `known_incidents` が持つ。
- 5xx (family のパターンから組み立てた URL) … `points: null` (G は unknown)。観測は残すが、そのサイトがその URL で公開しているか未確認なので、その配信元の継続性の根拠にしない。fukaya / gyoda の 2 行。
- 200 … `points: null` (unknown)。1 回取れたことは継続性の根拠にならない。design。
- `stable_url: true` 8 / `false` 3 … **design。** `stable_url` は未記録 (URL の形から恒久性は判断できない。時間をおいた再観測が要る)。
- `edition_label` (版表記) は段に使っていない。観測が 0 件で、有無を facts の等値で表す語彙も無い。

### 7.4 運用

- **`axes` は導出値。** `npm run apply-profile` が facts に段階表を当てて axes・provenance・`derived_at`・`profile`・`profile_revision` を書き戻す (コメントは保つ。同じ版・同じ結果なら何も変えない)。
- **`profile_revision` の照合。** `validate` が、assessment の `profile_revision` が `schema/profiles/<profile>.yaml` の `revision` と一致すること、保存済みの axes が facts から再導出した結果と一致することを検査する。段階表を変えたら `revision` を上げ、`apply-profile` で当て直す。
- **static 領域は段階表ファイルを持たない** (§6)。`gomi` など static の行は、axes を書いた行だけが採点でき、キャップも本 repo は持たない。facts だけの static 行は導出できないので失敗する。プロファイル未判定の領域 (`profile: null`) の facts だけの行も失敗する。
- **キャップの `when` は facts だけを見る。** 軸点や由来を条件にする必要は、現時点の実データに無い (今は不要)。必要になった時に語彙を足す。
- **`min_signals` の既定**は `scripts/_lib/family-check.mjs` の `DEFAULT_MIN_SIGNALS` (2) が正典で、`fingerprint.mjs` もそれを読む。

## 8. 総合点を作らない

(コア合計は §3.1。ここで言う総合点はコアと追加軸を足したもの。)

**コア 100 点と追加軸 F / G を合算した総合点は作らない。** 合算するとコア部分の横断比較が壊れる (追加軸のある領域とない領域が、同じ物差しで比べられなくなる)。

表示は併記とする。例: 「コア 82 / 動的 F:高 G:中」。併記の具体形式は実データを見てから決める。

## 9. 評価の単位

評価は**配信元ごと**に持つ。自治体値は配信元ごとの行から導出する。導出規則 (最良値・加重・カバレッジとの複合) は実データを見てから決める。**導出規則を先に固定しない。**
